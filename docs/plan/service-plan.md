# 서비스 기획서 — 업체 하나가 챗봇을 여럿 운영한다

> 계약은 [`docs/architecture/api-contracts.md`](../architecture/api-contracts.md) 가 진실 공급원이다.
> 이 문서는 **왜 나누는가, 어디까지 나누는가, 무엇을 나누지 않는가**를 적는다.

---

## 1. 지금 구조가 표현하지 못하는 것

`1 업체 = 1 챗봇 = 1 위젯 키` 가 스키마에 못 박혀 있다. `bot_settings` 는 `tenant_id` 가 곧 PK 이고
([`V2__tenant_dashboard.sql:19-21`](../../api/src/main/resources/db/migration/V2__tenant_dashboard.sql)),
그 위 주석은 이렇게 적혀 있다:

> 업체당 하나. `tenant_id` 가 곧 PK 다 — 1:N 이 될 일이 없는데 별도 id 를 두면
> "설정이 두 벌 생긴" 상태가 표현 가능해지고, 그러면 언젠가 실제로 생긴다.

**이번 작업은 그 결정을 뒤집는다.** "1:N 이 될 일이 없다"는 전제가 틀렸다.

지금 업체가 사이트 두 개를 운영하려면 길이 둘뿐이고 **둘 다 나쁘다**:

| 우회로 | 무엇이 깨지나 |
|---|---|
| `allowed_origins` 에 도메인 둘을 넣는다 | 같은 봇·같은 지식·같은 통계를 공유한다. **쇼핑몰 질문에 회사소개 문서로 답한다.** 대화 수·리드가 합쳐져 어느 사이트가 잘 되는지 알 수 없다 |
| 업체를 두 개 만든다 | 요금을 두 번 내고 담당자는 로그인을 번갈아 한다. `IMPROVEMENTS.md` P1 "한 이메일이 여러 업체에 속하는 경우 미지원"에 정면으로 걸린다 |

**이 트레이드오프를 언급한 문서가 프로젝트에 하나도 없었다.** 기획서·intake·결정표·IMPROVEMENTS
어디에도 없다 — 검토하고 미룬 것이 아니라 아예 다뤄지지 않았다.

## 2. 원칙

| 원칙 | 이유 |
|---|---|
| **챗봇 한 생이 통째로 갈린다** | 지식만 나누고 말투를 공유하면 "왜 여기서만 이상하게 답하지"가 생긴다. 반쯤 나누는 것이 가장 나쁘다 |
| **한도·요금·팀원은 업체 하나** | 계약의 단위는 업체다. 서비스마다 청구하면 연체가 서비스별로 갈려 "어느 것만 멈추나"를 매번 정해야 한다 |
| **서비스가 1개인 업체에게 이 기능은 존재하지 않는다** | 대다수가 그렇다. 배너 하나가 "내가 뭘 해야 하나"를 만든다 |
| **남의 사이트에 박힌 `<script>` 는 고칠 수 없다** | 스니펫 형태가 바뀌지 않는 설계여야만 한다. 이것이 모든 결정의 상한선이다 |
| **범위는 URL 에 있다** | 헤더·전역 상태로 두면 빠뜨릴 수 있고, 빠뜨리면 조용히 남의 데이터를 보여준다 |

## 3. 이름 — 코드는 `bot`, 화면은 "서비스"

`domain/{도메인}/service/` 가 레이어 관례다(25개 도메인 전부). 도메인을 `service` 로 만들면
**`domain/service/service/ServiceService.java`** 가 나온다. 쓸 수 없다.

이 리소스의 실체가 "챗봇 한 벌"이고 `botsettings` 도메인이 이미 있으므로 코드·API·DB 는 `bot`,
화면 문구만 "서비스"다.

**이 프로젝트는 원래 그렇게 해왔다** — `leads` → "남긴 연락처", `answer_gaps` → "답변 개선",
`faqs` → "공통 질문", `tenants` → "업체". 화면 용어와 스키마 용어가 일대일이었던 적이 없다.
대응표를 계약 문서에 한 줄로 못 박아 두 이름이 떠다니지 않게 한다.

## 4. 무엇을 나누고 무엇을 나누지 않나

### 4.1 나눈다 — 챗봇 한 생

`bot_settings`(말투·모양·노출 범위·런처) · `allowed_origins` · `knowledge_sources`
`knowledge_documents` · `knowledge_chunks` · `faqs` · `conversations` · `messages`
`message_feedback` · `leads` · `answer_gaps` · **위젯 키**

### 4.2 나누지 않는다

| 대상 | 이유 |
|---|---|
| 요금제 · 결제 · 청구 | 계약의 단위가 업체다 |
| 팀원 · 역할 | 지금 역할이 3단(OWNER/EDITOR/VIEWER)이고 JWT 클레임 하나다. 서비스 축을 곱하면 3×N 이 되고 토큰 구조까지 바뀐다. 요구에 포함돼 있지 않다 |
| 한도(대화·문서·원가) | **업체 합산**(§6) |
| `tenant_daily_usage` | §6.2 — 서비스를 지웠을 때 과거 업체 집계가 사라지면 안 된다 |
| `audit_logs` | 3년 불변 + UPDATE/DELETE 트리거. `meta` jsonb 에 `botId` 를 싣는다 |
| 알림 | 벨은 셸에 있다. 서비스를 바꿀 때마다 안 읽은 수가 달라지면 "알림이 사라졌다"가 된다. 대신 각 알림에 서비스 배지를 단다 |
| 대리 접속 세션 | 서비스로 좁혀도 운영자가 UI 에서 갈아타면 그만이라 **통제력이 늘지 않는다.** 실제 통제는 감사 기록 쪽이다 |

## 5. 위젯 — 계약이 한 글자도 바뀌지 않는다

위젯이 보내는 것은 키 하나뿐이라, 키가 업체를 가리키던 것이 서비스를 가리키게 되어도
**요청·응답 JSON 이 그대로다.** 남의 사이트에서 이미 도는 스니펫이 계속 동작한다 —
백필에서 **기존 키를 재발급하지 않고 첫 서비스로 옮기기만** 하면 된다.

서버 안에서만 바뀌는 세 곳:

```
key → bots.findByPublishableKey → bot
  ├ bot.status = ACTIVE                    (노출: 업체가 이 서비스를 켜뒀나)
  ├ tenant.status.servesVisitors()         (계약: 돈을 내는가)
  ├ allowed_origins WHERE bot_id = ?        ← 이 줄이 핵심이다
  └ Visitor(tenantId, botId, origin)
```

> **`allowed_origins` 조회를 서비스 범위로 바꾸지 않으면 격리가 뚫린다.** 지금은 한 업체의 모든
> 주소가 모든 키에 통용되므로, A 서비스 키를 B 서비스 도메인에 붙여도 통과한다.

**정지 판정은 2단계가 된다.** 다만 계약 상태(정지·해지)는 결제 사유라 **업체 단위이고 전 서비스가
함께 멈춘다** — 과금이 합산이라 부분 정지에 의미가 없다.

### 5.1 UUID 두 개를 나란히 넘기지 않는다

`ask(UUID tenantId, UUID botId, …)` 처럼 같은 타입 UUID 둘이 나란히 다니면 **언젠가 순서가 바뀌고
컴파일러가 못 잡는다.** 그 결과는 타 업체 데이터 조회이므로 P0 다.

```java
/** 위젯·대시보드가 다루는 범위. tenantId 와 botId 를 절대 따로 넘기지 않는다. */
public record BotScope(UUID tenantId, UUID botId) { }
```

리포지토리 층에서만 풀어 쓴다.

### 5.2 같은 페이지에 스니펫 둘을 붙이면

허용은 한다 — 한 사이트의 `/shop` 과 `/support` 에 다른 봇을 붙이는 것은 정당하고,
`PagePatternMatcher` 의 노출 범위가 정확히 그것을 위해 있다.

**단 같은 페이지에 둘을 붙이면 하나만 뜬다.** `loader.tsx` 의 중복 삽입 가드와 전역 키
(`window.dabhaejwo`) 가 하나뿐이라, 두 번째 스크립트는 아무것도 하지 않는다. 어느 쪽이 살아남는지는
스크립트 순서가 정한다. 설치 화면이 이 사실을 경고한다 — 겪고 나서 알게 두지 않는다.

## 6. 한도와 요금

### 6.1 바뀌지 않는 것 — 이름으로 못 박는다

대화 수·문서 수·일일 원가 상한은 **전부 업체 합산으로 남는다.** `bot_id` 가 생겼다고 서비스별로
세는 실수를 막기 위해 메서드 이름에 의도를 박는다:

`countAnsweredAcrossBots(tenantId, …)` · `countActiveDocumentsAcrossBots(tenantId)`

이름이 "AcrossBots" 라고 말하면 다음 사람이 실수하지 않는다.

### 6.2 서비스별 사용량은 별도 테이블

`tenant_daily_usage` 의 PK 를 `(tenant_id, bot_id, day)` 로 바꾸고 합산으로 롤업하고 싶어지지만
**바꾸지 않는다** — 그러면 **서비스를 지웠을 때 과거 업체 매출·원가 집계가 함께 사라진다.**
서비스별 집계는 `bot_daily_usage` 를 새로 만들고 같은 배치가 두 축을 채운다.

`ai_usage.bot_id` 는 **nullable 이고 FK 를 걸지 않는다.** 서비스는 지워지는데 원장은 남아야 한다 —
CASCADE 면 원장이 지워지고 SET NULL 이면 원가 귀속이 소급 변경된다. 둘 다 "원가는 호출 시점에
확정, 소급 금지"(`CLAUDE.md`) 위반이다. 과거 행은 **0 이나 기본값으로 채우지 않는다** —
`latency_ms` 를 0으로 채우지 않은 것과 같은 이유다.

### 6.3 `plans.bot_limit`

**기존 5개 요금제에 전부 `1` 을 준다.** 백필로 모든 업체가 정확히 1개를 갖게 되므로
**아무도 위반 상태가 되지 않는다.** 이것이 유일하게 안전한 값이다.

BUSINESS 를 3으로 박고 싶어지지만 박지 않는다 — 그건 가격 정책 결정이고, 마이그레이션에 넣으면
되돌리는 데 또 마이그레이션이 필요하다. `plans` 는 이미 운영 콘솔에서 편집 가능하다.

검사는 **생성 시점에만** 한다. 상한을 내려도 기존 서비스를 강제로 지우지 않는다 —
이미 남의 사이트에서 도는 위젯을 요금제 변경으로 조용히 죽이면 방문자에게는 장애로 보인다.
`sellable=false` 로 판매만 중단하고 기존 계약은 남기는 철학과 같다.

에러는 `BOT_LIMIT_REACHED`(409)다. `QUOTA_EXCEEDED`(429)를 재사용하지 않는 이유는 429 가
"기다리면 풀린다"는 뜻이기 때문이다 — 서비스 상한은 기다려도 안 풀리고, 화면이 안내할 다음 행동
(요금제 변경)이 완전히 다르다.

## 7. 화면

### 7.1 URL 은 경로 세그먼트 — `/app/s/{botId}/faq`

전역 선택 상태로 두면 **두 서비스를 두 탭에 띄울 수 없다.** 한쪽을 바꾸면 다른 쪽이 다음
조회에서 조용히 따라 바뀐다. 그런데 **여러 서비스를 나란히 비교하는 것이 이 기능의 주 사용자가
하는 일 그 자체다.**

`/s/` 표식을 넣는 이유는 `/app/plan`·`/app/team` 과 첫 세그먼트가 자리를 다투지 않게 하기
위해서다. URL 에 `/s/` 가 있으면 서비스별, 없으면 업체 단위 — 화면을 안 봐도 읽힌다.

**기존 경로를 지우지 않는다.** `notifications.target_path` 에 `/app/leads` 같은 절대 경로가
**이미 DB 에 저장돼 있다.** `/app/{화면}` 을 현재 서비스로 `replace` 시킨다(`push` 면 뒤로가기가
루프에 걸린다). 과거 행 일괄 UPDATE 와 리다이렉트를 **둘 다** 한다.

`/app` 착지 규칙 — 서비스 1개면 그 서비스로, 2개 이상이면 `/app/services` 목록으로.
**별도의 "업체 합산 홈"을 만들지 않는다.** 합산 지표는 어떤 행동도 유발하지 않는다.
목록의 각 행이 "어느 서비스를 지금 봐야 하는가"만 답한다.

### 7.2 화면 판정

| 서비스별 (`/app/s/{botId}/…`) | 업체 단위 (`/app/…`) |
|---|---|
| 홈 · 답변 개선 · 대화 로그 · 남긴 연락처 | 요금제 · 팀원 |
| 지식 소스 · 공통 질문 · 말투 · 위젯 관리 · 설치 | **서비스 목록 / 추가**(신규 2개) |

- **지식 소스**: 목록은 서비스별이지만 **한도 표시는 업체 합산**이다. "업체 전체 248 / 500" 이라고
  범위를 밝히지 않으면 "내 서비스는 40개인데 왜 한도 초과냐"가 된다
- **공통 질문**: `followUpFaqIds` 는 같은 서비스 안에서만 유효하다. 서비스 간 참조를 허용하면
  위젯이 남의 사이트 답변을 칩으로 띄운다
- **남긴 연락처**: 업체 통합 CSV 내보내기를 만들지 않는다. 연락처 원문이 나가는 유일한 경로라
  범위를 넓히면 유출 반경이 커진다

**사이드바 항목 수는 11개 그대로다.** 서비스 목록으로 가는 길은 셀렉터 하단의 `서비스 관리` 와
요금제 화면의 `서비스 1 / 3` 행, 둘뿐이다.

### 7.3 전환 UI — 이미 있는 자리를 넓힌다

사이드바 상단에 업체 이름 + 도메인 블록이 이미 있다. 새 자리를 만들지 않고 이 블록이 역할을 넓힌다.

- **서비스 1개 — 지금과 렌더 트리가 같다.** 버튼도, 드롭다운 표식도, `aria-haspopup` 도 붙이지
  않는다. 스크린 리더에 "메뉴 버튼"이라고 읽히는 것부터가 새 복잡함이다
- **2개 이상** — 같은 블록이 버튼이 되고, 각 항목에 작동 상태 점 + **텍스트 라벨**을 단다
  (색만으로 구분하지 않는다)

전환 시 같은 화면을 유지하되 **상세 id 와 검색·필터 쿼리는 버린다.** A 에서 "환불"로 검색하던
상태를 B 로 옮기면 0건이 뜨는데, 사용자는 그걸 "B 에는 대화가 없다"로 읽는다.

"현재 서비스"의 진실은 **URL 뿐이다.** 최근 방문 서비스는 `sessionStorage` 에만 둔다
(`localStorage` 는 탭 공유라 두 탭 시나리오를 다시 깨뜨린다) — 그것도 **링크가 가리킬 곳을 고르는
용도로만** 쓰고 데이터 조회의 근거로는 절대 쓰지 않는다.

### 7.4 서비스 목록 · 추가

- 목록은 테이블이다. 행마다 서비스명 · 도메인 · 작동 상태 · 오늘 대화 · 미해결 개선 건수
- **서비스별 설정 화면을 따로 만들지 않는다.** 이름 변경·삭제는 목록의 행 액션이다 —
  그러면 **보고 있는 화면을 삭제하는 상황 자체가 생기지 않는다**
- 추가는 모달이 아니라 페이지다. 입력은 **이름 + 대표 도메인 둘뿐**이고, 만들면
  **바로 설치 화면으로 보낸다** — 새 서비스의 유일한 다음 행동이 코드 붙이기다
- 상한에 닿아도 **[서비스 추가] 버튼을 숨기지 않는다.** 눌렀을 때 안내한다. 숨기면 왜 없는지
  알 수 없고, 서비스 수 상한 자체가 요금제 판매 포인트라 보여야 한다

## 8. 운영 콘솔

- **목록에 컬럼을 늘리지 않는다.** 서비스 수는 그 자체로 조치를 부르는 숫자가 아니다.
  업체 셀의 부제만 `nordheim.co.kr 외 2` 로 바꾸고, **1이면 지금과 글자 하나 안 다르다**
- **검색 `q` 가 서비스 이름·도메인·키를 반드시 잡아야 한다.** 키는 이제 업체에 없으므로,
  안 고치면 **위젯 키로 업체를 찾는 CS 경로가 통째로 죽는다**
- **상세에 탭을 도입하지 않는다.** 왼쪽 열 "계정"과 "조치" 사이에 서비스 카드를 끼운다 —
  대리 로그인을 누르기 직전에 어느 서비스로 들어갈지 바로 위에서 본다
- 이 카드가 **운영 콘솔에서 허용 도메인을 처음 보게 되는 지점**이다. CS 문의 1순위가 "코드 붙였는데
  안 떠요"이고 원인 대부분이 미등록 주소인데, 지금은 그걸 보려고 사유를 적고 대리 로그인을 해야 한다
- 대리 접속은 서비스를 **선택 인자**로 받고 응답에 진입 경로를 담는다. 경로를 서버가 만드는 이유는
  admin·tenant 두 프로젝트가 각자 URL 규칙을 적기 시작하면 갈리기 때문이다
- **감사 기록 `meta.serviceId`** — 안 남기면 "어느 서비스의 고객 데이터를 봤나"가 영영 기록되지
  않는다. 3년 보존·수정 불가라 나중에 채울 수 없다

## 9. 삭제

| 규칙 | 이유 |
|---|---|
| **마지막 서비스는 지울 수 없다** | `allowed_origins` 의 "마지막 주소는 지울 수 없습니다"와 같은 원리 |
| **즉시 파기하지 않는다** — 위젯은 즉시 멈추고 데이터는 유예 | 실수로 지운 업체를 되살릴 수 있다. `cost_guards.churn_purge_grace_days` 를 그대로 쓴다 |
| OWNER 전용 · 대리 접속 중 금지 | 운영자가 남의 서비스를 통째로 지우는 일은 없어야 한다 |
| 이름 타이핑 확인 + **무엇이 사라지는지 명시** | "대화 로그 · 남긴 연락처 · 학습 문서가 함께 사라집니다". 안 적으면 지운 뒤에 알게 된다 |
| `ai_usage` · `audit_logs` 는 남긴다 | 원가와 감사는 불변 |

**다른 탭에서 삭제된 경우** API 는 404 를 주고 화면은 "이 서비스는 삭제되었습니다"를 명시한다.
**조용히 다른 서비스로 갈아타지 않는다** — 갈아타면 사용자는 남의 서비스 대화 로그를 자기 것으로 읽는다.

> **이것이 이 시스템 최초의 purge 배치다.** `tenants.purge_after` 는 해지 시 채워지지만
> **읽는 코드가 없다** — "해지된 업체 데이터를 지운다"는 약속이 코드에 없다. 서비스 purge 워커가
> 두 축을 함께 처리하게 만들어 그 부채도 같이 갚는다. 순서가 중요하다:
> **R2 오브젝트 → chunks → documents → 나머지 → bots 행.** 반대로 하면 R2 에 고아 오브젝트가
> 남고 그것을 찾을 키가 사라진다.

## 10. 조용히 깨질 곳

| 위험 | 왜 |
|---|---|
| **벡터 검색에 서비스 필터 누락** | A 서비스 질문에 B 문서가 근거로 나간다. **오류도 로그도 없이 "답이 이상하다"로만 보인다** |
| **`...ByTenantId...` 리포지토리 메서드가 남는다** | 컴파일러가 못 잡는다. ⭐ **가장 효과적인 방어는 그 메서드를 지우는 것이다** — 남겨두면 언젠가 쓰인다. 한도·집계용으로 필요한 것만 `...AcrossBots` 로 개명 |
| **`answer_gaps` upsert 가 다른 서비스 행을 갱신** | 위 항목의 구체적 사례. 둘 다 UUID라 실수해도 안 터지고 **조용히 잘못된 행을 갱신**한다 |
| **파일 소스가 업체당 하나** | `findFirstByTenantIdAndType(tenantId, FILE)` 를 그대로 두면 모든 서비스 업로드가 한 소스에 쌓인다 |
| **미리보기가 어느 서비스인지 모른다** | `ChatPreviewController` 가 tenantId 로 답을 만든다. 안 고치면 미리보기가 아무 지식이나 긁는다 |
| **저장소 키에 서비스 접두사가 없다** | `tenants/{tenantId}/…` 라 서비스 하나만 접두사로 지울 수 없다. 신규 업로드부터 나눈다 |
| **공개 자산 URL** | **옮기지 않는다.** 계약 §10-3 이 "옛 파일을 지우지 않는다 — 그 URL 을 담아 응답한 위젯이 남의 사이트에서 아직 돈다"고 못 박고 있다. 저장 키만 나누고 공개 경로 형태는 그대로 |
| **로컬 시드** | 서비스 없이 데이터를 만들면 배포 전에 안 걸리고 로컬에서만 깨진다 |

## 11. 단계

| | 내용 | 합격 조건 |
|---|---|---|
| **M1** | 스키마·백필만(V16). 코드 변경 0 | **기존 앱이 그대로 뜨고 위젯이 그대로 답한다.** 여기서 깨지면 되돌리기가 `DROP TABLE` 몇 개다 |
| **M2** | 읽기·쓰기 경로가 서비스 기준으로. **서비스는 여전히 1개** | **관찰 가능한 동작이 하나도 바뀌지 않는다.** 가장 위험한 구간이지만 회귀 판정이 명확하다 |
| **M3** | 서비스가 여럿이 된다 — CRUD·상한·라우팅·셀렉터·알림 경로 | 여기서부터 제품 결정이 들어간다. M2 까지는 순수 리팩터링이다 |
| **M4** | 삭제·유예·purge 워커 | 되돌릴 수 없는 기능이라 나머지가 안정된 뒤 붙인다. **M4 없이 M3 은 안전하다**(못 지울 뿐) |

**M2 의 "동작 불변" 경계가 이 계획의 핵심이다.** 그 구간을 따로 떼면, M3 에서 뭔가 깨졌을 때
원인이 배선이 아니라 새 기능임을 안다.

### 마이그레이션이 지켜야 할 두 가지

1. **이미 박힌 `pk_live_*` 가 계속 동작한다** — 키를 새로 뽑지 않는다
2. **V16 은 아무것도 `DROP` 하지 않고 아무것도 `NOT NULL` 로 만들지 않는다** —
   `ddl-auto: validate` 라 마이그레이션과 배포가 사실상 동시다. 컬럼을 먼저 지우면
   구버전으로 롤백하는 순간 API 가 기동조차 못 한다. **Hibernate 의 validate 는 "DB 에 있는데
   매핑에 없는 컬럼"을 문제 삼지 않고 PK·nullability 도 검사하지 않는다** — 그래서
   "매핑 먼저 제거 → 컬럼 나중 제거", "nullable 백필 먼저 → 나중에 조이기"가 가능하다

백필 끝에 **어서션을 넣는다** — 채워지지 않은 행이 하나라도 있으면 마이그레이션을 실패시킨다.
절반만 채워진 채 통과하면 다음 마이그레이션에서야 발견되고, 그때는 이미 배포돼 있다.
PostgreSQL 은 DDL 이 트랜잭션이라 실패하면 통째로 되감긴다 — 이것이 안전망이다.

마이그레이션이 만드는 서비스의 이름은 **업체명을 그대로 쓴다.** `"서비스 1"` 로 두면 두 번째를
만들 때 셀렉터에 `서비스 1 / 아울렛` 이 뜬다.

## 12. 이번 범위 밖 (기록만)

| 항목 | 비고 |
|---|---|
| 서비스별 팀원 권한 | 역할 3단 × 서비스 N 이 되고 토큰 구조가 바뀐다. `member.botIds: null`(전체)로 나중에 열 수 있는 형태만 계약에 남긴다 |
| 위젯 키 회전 | 진짜 회전은 구키를 유예 기간 동안 함께 받아야 하므로 `bot_keys` 테이블이 답이다. 반쪽 컬럼을 지금 넣으면 그때 버려진다. **다만 키를 `bots` 로 옮기는 것 자체가 그 승격을 가능하게 만든다** |
| `quota_overrides` 가 한도에 반영되지 않음 | `ChatGuard` 는 요금제 원본만 본다. **기존 갭이며 이번 작업과 무관** — "한도 재설계"에 끌려 들어오지 않게 명시해 둔다 |
| 업체 담당자 행위의 감사 기록 | `audit_logs.operator_id` 가 NOT NULL 이라 업체 행위를 남길 곳이 없다. 서비스 삭제는 되돌릴 수 없는 업체 행위인데 기록할 데가 없다 |
| 계약↔코드 기존 불일치 2건 | ① `q` 가 담당자 이메일을 잡는다고 적혀 있으나 코드는 안 잡는다 ② `GET /api/app/impersonation/current` 가 계약에 있으나 코드에는 `/me` 의 필드로만 있다 |
