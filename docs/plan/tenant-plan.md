## 1. 개요

### 1.1 시스템 내 위치

| 구분 | 사용자 | 목적 |
|---|---|---|
| 임베드 위젯 | 업체 사이트 방문자 | 질문하고 답변받기 |
| **업체 대시보드** | **업체 담당자** | **자기 챗봇을 학습시키고 개선하기** |
| 운영 콘솔 | 자사 운영팀 | 서비스 전체 운영 |

이 문서는 두 번째를 다룬다.

### 1.2 사용자

계약한 업체의 담당자다. **개발자가 아닌 경우가 대부분**이며, 실제로는 다음과 같은 사람들이다.

| 유형 | 특징 | 이 화면에서 하는 일 |
|---|---|---|
| 쇼핑몰 운영자 | 혼자 다 함. 시간이 없음 | 설치하고, 가끔 답변 보충 |
| CS 담당 | 고객 문의를 매일 봄 | 답변 개선, 연락처 확인 |
| 마케터 | 전환율에 관심 | 통계, 리드 수집 |
| 외주 개발자 | 설치만 하고 떠남 | 임베드 코드 삽입 |

### 1.3 설계상 가장 중요한 전제

**이 사람들은 RAG도, 임베딩도, 벡터도 모른다.** 알 필요도 없다. 화면 어디에도 이런 용어가 나와서는 안 된다.

| 쓰지 않을 말 | 대신 쓸 말 |
|---|---|
| 크롤링 | 사이트 다시 읽기 |
| 임베딩 · 인덱싱 | 학습 |
| 청크 | (노출하지 않음) |
| 벡터 · 유사도 | (노출하지 않음) |
| API 키 | 홈페이지에 붙일 코드 |
| 토큰 | 대화 수 |
| 프롬프트 | 말투 |
| 폴백 | 모를 때 할 말 |

### 1.4 이 화면이 성공하는 조건

업체가 계속 돈을 내게 만드는 건 두 가지다.

1. **설치가 끝난다** — 가입 후 30분 안에 챗봇이 자기 사이트에 떠 있어야 한다
2. **좋아진다는 감각** — 답을 못 한 질문에 답을 채우면 챗봇이 실제로 나아진다는 것을 눈으로 확인해야 한다

두 번째가 없으면 첫 달만 쓰고 해지한다. 그래서 대시보드의 중심은 통계가 아니라 **개선 루프**여야 한다.

## 2. 설계 원칙

### 2.1 첫 화면은 오늘 할 일 하나만 보여준다

지표 카드를 나열하면 무엇을 해야 할지 사라진다. 최상단에는 문장 하나만 크게 둔다.

> 오늘 들어온 **128**건의 질문 중 **9**건은 답하지 못했습니다.

이 문장이 곧 행동 유도다. 숫자를 누르면 그 목록으로 간다.

### 2.2 개선 루프를 화면 구조로 만든다

```
방문자 질문 → 답변 실패 → 목록에 쌓임 → 업체가 답 등록 → 다음부터 챗봇이 답함
```

이 순환이 끊기지 않도록, 실패한 답변이 보이는 모든 자리(대화 로그, 홈, 답변 개선)에 **"여기에 답 달기"** 버튼을 둔다.

### 2.3 출처를 항상 보여준다

답변 아래에 참조한 페이지·문서를 링크로 붙인다. 업체가 "챗봇이 어디서 이런 말을 가져왔지?"를 즉시 확인할 수 있어야 신뢰가 생기고, 틀린 답의 원인도 추적된다.

### 2.4 설정은 한 곳에서만 한다

같은 값을 두 화면에서 고칠 수 있으면 반드시 어긋난다. 예를 들어 채팅창에 뜨는 질문 문구는 **공통 질문에서만** 관리하고, 말투 설정 화면에서는 현재 몇 개가 노출 중인지와 바로가기만 보여준다.

## 4. 화면별 상세

### 4.1 홈

**목적** 오늘 무엇을 해야 하는지 3초 안에 파악한다.

| 영역 | 내용 |
|---|---|
| 헤드라인 | 오늘 대화 수와 답변 실패 건수를 문장으로 + 이동 버튼 |
| 지표 4종 | 오늘 대화, 답변 성공률, 남긴 연락처, 평균 응답 시간 |
| 지식 상태 | 학습 완료·처리 중·실패를 색 막대로 압축 + 실패 재학습 버튼 |
| 많이 물어본 질문 | 최근 7일 상위 5개 |

**지식 상태 막대**는 문서 수백 개의 상태를 스크롤 없이 한눈에 보여주기 위한 장치다. 빨간 칸이 보이면 실패한 문서가 있다는 뜻이고, 바로 아래 버튼으로 재학습한다.

---

### 4.2 답변 개선 ★

**목적** 챗봇이 답하지 못한 질문에 답을 채워 넣는다. 이 서비스의 심장이다.

**목록에 올라오는 것**

| 유형 | 조건 |
|---|---|
| 답변 실패 | 관련 문서를 찾지 못해 모른다고 답한 경우 |
| 👎 받음 | 방문자가 부정 피드백을 남긴 경우 |

**항목 구성**

- 질문 원문
- 발생 횟수 (같은 취지의 질문을 묶어 표시)
- 최근 발생 시각과 유입 페이지
- 챗봇이 실제로 뭐라고 답했는지
- 답변 입력창 + 등록 버튼

**동작**

1. 항목을 펼치면 챗봇의 실패 답변이 보인다
2. 답을 입력하고 등록하면 **공통 질문에 자동 저장**된다
3. 등록 즉시 다음 질문부터 적용된다
4. 목록에서 사라지고, 며칠 뒤 "이 답변이 N번 쓰였습니다" 알림으로 성과를 알린다

**유사 질문 묶기**

"제주 배송되나요", "제주도까지 오나요", "도서지역 배송" 은 같은 질문이다. 개별로 쌓이면 목록이 지저분해지고 업체가 지친다. 질문 임베딩의 유사도로 묶어 대표 질문 하나로 보여준다.

**보조 액션**

| 버튼 | 동작 |
|---|---|
| 답변 등록 | 공통 질문에 저장 |
| 관련 문서 추가 | 지식 소스 추가 모달 열기 |
| 넘어가기 | 목록에서 숨김. 다시 발생하면 재등장 |

---

### 4.3 대화 로그

**목적** 방문자와 챗봇이 실제로 어떤 대화를 했는지 확인한다.

**구성** 좌측 목록 + 우측 상세의 분할 배치

| 목록 항목 | 상세 |
|---|---|
| 방문자 구분(지역 또는 이름) | 전체 대화 내용 |
| 시각 | 시작 페이지, 소요 시간 |
| 첫 질문 미리보기 | 답변별 출처 링크 |

**필터** 기간, 답변 실패만, 👎 받은 것만, 연락처 남긴 것만

**실패 답변 표시** 답을 못 한 말풍선은 배경색을 달리하고 **"여기에 답 달기"** 버튼을 붙인다. 대화를 읽다가 바로 개선으로 넘어갈 수 있어야 한다.

**개인정보** 방문자가 대화 중 남긴 연락처는 뒷자리를 마스킹해 표시한다.

---

### 4.4 남긴 연락처

**목적** 챗봇이 답하지 못했을 때 수집한 리드를 관리한다.

| 컬럼 | 내용 |
|---|---|
| 이름 | |
| 연락처 | 마스킹 표시, 클릭 시 전체 노출 |
| 남긴 이유 | 어떤 질문 끝에 남겼는지 |
| 시각 | |
| 처리 상태 | 대기 / 연락함 / 종료 |

**액션** CSV 내보내기, 알림 설정(이메일·슬랙)

업체 입장에서 이 화면이 곧 매출이다. 챗봇의 값어치를 숫자로 보여주는 유일한 곳이므로, 요금제 갱신 시점에 이 지표를 강조한다.

### 4.5 지식 소스

**목적** 챗봇이 참고할 자료를 등록하고 상태를 확인한다.

**탭 구성**

| 탭 | 내용 |
|---|---|
| 웹페이지 | 사이트 주소 등록 → 하위 페이지 목록 → 포함/제외 선택 |
| 파일 | PDF·Word·엑셀 업로드 |
| 직접 입력 | 사이트에 없는 내용을 글로 작성 |

**웹페이지 탭**

1. 주소를 넣으면 sitemap과 링크를 따라 하위 페이지를 찾는다
2. 찾은 페이지를 목록으로 보여주고 체크박스로 고르게 한다
3. 선택한 것만 학습한다
4. 자동 갱신 주기를 설정한다 (기본 주 1회)

전부 자동으로 학습하지 않고 **고르게 하는 것**이 중요하다. 채용 공고나 이용약관처럼 챗봇이 답할 필요 없는 페이지가 섞이면 답변 품질이 떨어진다.

**파일 탭**

- 드래그앤드롭, 다중 업로드
- 파일당 최대 20MB
- 처리 상태를 실시간 표시

**스캔 PDF 처리** 글자를 추출하지 못한 경우 "이 파일에서 글자를 찾지 못했습니다. 스캔한 문서로 보입니다"라고 명확히 안내한다. 조용히 실패하면 업체는 학습된 줄 알고 기다린다.

**직접 입력 탭**

매장 운영시간, 임시 공지, 이벤트 안내처럼 페이지로 만들지 않은 정보를 넣는 곳이다.

### 4.6 공통 질문

**목적** 자주 오는 질문에 미리 답을 만들어 두고, 채팅창에 버튼으로 노출한다.

**동작**

- 등록한 질문이 채팅창을 열었을 때 버튼으로 보인다
- 방문자가 버튼을 누르면 **AI가 답을 만들지 않고 저장된 답변을 그대로** 보여준다
- 즉시 표시되고, 대화 사용량에 포함되지 않는다

**항목 구성**

| 필드 | 설명 |
|---|---|
| 질문 | 버튼에 보일 문구. 20자 이내 권장 |
| 답변 | 저장할 답변 원문 |
| 함께 보여줄 문서 | 답변 아래 링크로 붙음 |
| 노출 여부 | 끄면 버튼에는 안 보이지만, 직접 입력 시에는 사용됨 |
| 후속 질문 | 답변 뒤에 이어 제안할 질문 |

**노출 토글의 의미**

| 상태 | 버튼 노출 | 직접 입력 시 매칭 |
|---|:--:|:--:|
| 켬 | ● | ● |
| 끔 | ○ | ● |

노출을 끈 항목도 방문자가 비슷한 내용을 입력하면 저장 답변이 나간다. 자주 묻지는 않지만 답이 정해진 질문(세금계산서, 경쟁사 비교 등)에 쓴다.

**순서 조정** 위아래 화살표로 버튼 순서를 바꾼다. 가장 중요한 질문이 위로 온다.

**미리보기** 화면 옆에 실제 채팅창을 띄워 즉시 확인한다.

### 4.7 말투와 모양

**목적** 챗봇의 성격과 외형을 정하고, 바로 확인한다.

**모양**

| 항목 | 비고 |
|---|---|
| 챗봇 이름 | |
| 프로필 이미지 | 없으면 이름 첫 글자 |
| 버블 색상 | 프리셋 4종 + 직접 입력 |
| 첫 인사말 | |
| 처음 보이는 질문 버튼 | **공통 질문으로 링크만** — 여기서 수정하지 않음 |

**말투**

| 항목 | 설명 |
|---|---|
| 어떤 태도로 답할까요 | 업체가 자유 서술. 3~4문장 권장 |
| 모를 때 할 말 | 답변 실패 시 문구 |
| 말하지 말 것 | 타사 비교, 할인 협상 등 금지 주제 |

**답을 못 찾았을 때**

| 옵션 | 기본값 |
|---|---|
| 연락처 남기기 제안 | 켬 |
| 고객센터 번호 안내 | 켬 |
| 운영시간에는 상담원 연결 | 끔 (2차) |

**미리보기**

화면 오른쪽에 실제 위젯을 띄우고, 설정을 바꾸면 즉시 반영한다. **여기서 직접 질문해볼 수 있어야 한다.** 배포 전에 업체가 스스로 품질을 확인하고 튜닝하는 자리이며, 이 경험이 없으면 지식을 채울 동기가 생기지 않는다.

### 4.8 설치

**목적** 홈페이지에 챗봇을 띄운다. **가입 후 가장 먼저 넘어야 할 관문이다.**

**구성**

| 영역 | 내용 |
|---|---|
| 임베드 코드 | 복사 버튼 + 붙여넣을 위치 안내 |
| 연결 상태 | 실제 호출이 들어오면 자동으로 "연결 확인됨"으로 전환 |
| 허용 주소 | 도메인 등록·삭제, 도메인별 작동 상태 |
| 플랫폼별 가이드 | 카페24, 아임웹, 워드프레스, 그누보드 |
| 최근 호출 | 시각·경로·응답 코드 |

**임베드 코드**

```html
<script>
  window.dabhaejwo = { key: "pk_live_a8f3k2m9x7q1" };
</script>
<script src="https://cdn.dabhaejwo.com/w.js" async></script>
```

이 키는 브라우저에 노출되므로 비밀이 아니다. 등록한 도메인에서만 동작하도록 서버가 `Origin`을 검증한다. 화면에도 **"이 키는 공개돼도 괜찮습니다"** 라고 명시해 업체의 불안을 없앤다.

**연결 확인 자동화**

코드를 붙였는데 안 뜨는 상황이 가장 흔한 이탈 지점이다. 실제 호출이 들어오면 화면 상태가 자동으로 바뀌게 해서, 업체가 "됐는지 안 됐는지" 헤매지 않게 한다.

**개발자에게 보낼 링크**

직접 설치가 어려운 업체를 위해, 코드와 설치 안내가 담긴 공유 링크를 복사하는 버튼을 둔다. 외주 개발자에게 그대로 전달하면 된다.

### 4.9 요금제

| 영역 | 내용 |
|---|---|
| 현재 요금제 | 이름, 월 요금, 다음 결제일 |
| 사용량 | 대화 수, 학습 문서 수 (한도 대비 막대) |
| 액션 | 요금제 변경, 결제 수단, 세금계산서 |
| 결제 내역 | 날짜, 항목, 금액, 영수증 |

**한도 알림** 80%와 100% 도달 시 화면 배너와 이메일로 알린다. 갑자기 챗봇이 멈추는 경험은 해지로 직결된다.

**절약 안내** 공통 질문으로 처리된 비율을 함께 보여준다. "이번 달 대화의 39%는 저장된 답변으로 처리되어 한도를 쓰지 않았습니다" 같은 문구는 공통 질문 등록을 유도한다.

## 6. 온보딩

가입 직후 30분이 이 서비스의 승부처다. 여기서 막히면 대부분 돌아오지 않는다.

### 6.1 흐름

```
가입 → 사이트 주소 입력 → 페이지 자동 탐색 → 학습(2~5분)
     → 미리보기에서 직접 질문 → "오, 되네" → 임베드 코드 복사 → 설치 확인
```

### 6.2 핵심 설계

**학습을 기다리는 동안 미리보기를 열어둔다.** 진행률만 보여주면 지루하고, 이탈한다. 먼저 학습된 페이지부터 답할 수 있게 해서 **완료 전에 이미 동작하는 것을 보게** 한다.

**첫 질문을 대신 만들어 준다.** 학습된 내용에서 자동으로 3~4개의 질문을 뽑아 제시한다. 빈 채팅창 앞에서 뭘 물어야 할지 모르는 상태를 없앤다.

**설치 단계까지 체크리스트로 안내한다.**

| 단계 | 완료 조건 |
|---|---|
| 1. 사이트 등록 | 페이지 1개 이상 학습 완료 |
| 2. 챗봇 확인 | 미리보기에서 1회 이상 대화 |
| 3. 설치 | 실제 도메인에서 호출 발생 |
| 4. 공통 질문 | 1개 이상 등록 |

4번을 온보딩에 넣는 이유는 원가 때문이다. 공통 질문이 0개인 업체는 모든 대화가 AI로 처리되어 원가율이 급격히 오른다. 시작 단계에서 습관을 만들어 두는 편이 서로에게 낫다.

## 7. 데이터 모델

> ⚠️ **이 절은 개념 모델이다. 구현의 진실은 `api/src/main/resources/db/migration/` 의 마이그레이션이다.**
> 컬럼명·테이블명이 다르면 마이그레이션이 맞다. 실제 스키마는 여기서 더 나뉘어 있다 —
> 소스와 문서를 `knowledge_sources` / `knowledge_documents` 로 분리했고(사이트 한 곳에 페이지가 수백 장이다),
> 피드백은 `message_feedback` 로 뺐다(메시지마다 null 컬럼을 두지 않으려고).
> boolean 은 `is` 접두사를 쓰지 않는다(`shown`) — `.claude/rules/api-contract-rules.md`.

```sql
-- 지식 소스 (사이트 · 파일 · 직접 입력)
CREATE TABLE sources (
  id          uuid PRIMARY KEY,
  tenant_id   uuid NOT NULL,
  kind        text NOT NULL,   -- site | file | manual
  title       text NOT NULL,
  url         text,
  storage_key text,            -- R2 오브젝트 키
  status      text NOT NULL,   -- pending | processing | ready | failed | excluded
  error_code  text,
  auto_refresh boolean DEFAULT false,
  last_indexed_at timestamptz,
  created_at  timestamptz DEFAULT now()
);
CREATE INDEX ON sources (tenant_id, status);

-- 문서 조각
CREATE TABLE chunks (
  id         bigserial PRIMARY KEY,
  tenant_id  uuid NOT NULL,
  source_id  uuid NOT NULL REFERENCES sources(id) ON DELETE CASCADE,
  content    text NOT NULL,
  page_no    int,             -- PDF 출처 표시용
  embedding  vector(1536) NOT NULL,
  created_at timestamptz DEFAULT now()
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON chunks (tenant_id);

-- 공통 질문
CREATE TABLE faqs (
  id          uuid PRIMARY KEY,
  tenant_id   uuid NOT NULL,
  question    text NOT NULL,
  answer      text NOT NULL,
  q_embedding vector(1536),   -- 직접 입력 매칭용
  link_titles text[],
  follow_ids  uuid[],
  is_shown    boolean DEFAULT true,
  sort_order  int NOT NULL,
  hit_count   int DEFAULT 0,
  created_at  timestamptz DEFAULT now()
);

-- 대화
CREATE TABLE conversations (
  id          uuid PRIMARY KEY,
  tenant_id   uuid NOT NULL,
  session_key text NOT NULL,
  entry_path  text,
  region      text,
  started_at  timestamptz DEFAULT now()
);

CREATE TABLE messages (
  id          bigserial PRIMARY KEY,
  conv_id     uuid NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  role        text NOT NULL,   -- visitor | bot
  content     text NOT NULL,
  answer_type text,            -- faq | generated | failed
  source_ids  uuid[],
  feedback    smallint,        -- 1 | -1 | null
  created_at  timestamptz DEFAULT now()
);
CREATE INDEX ON messages (conv_id, created_at);

-- 개선 대상 질문 (유사 질문 묶음)
CREATE TABLE answer_gaps (
  id          uuid PRIMARY KEY,
  tenant_id   uuid NOT NULL,
  sample_q    text NOT NULL,
  q_embedding vector(1536) NOT NULL,
  occurrences int DEFAULT 1,
  status      text DEFAULT 'open',  -- open | resolved | dismissed
  resolved_faq_id uuid,
  last_seen_at timestamptz DEFAULT now()
);

-- 수집된 연락처
CREATE TABLE leads (
  id         uuid PRIMARY KEY,
  tenant_id  uuid NOT NULL,
  conv_id    uuid,
  name       text,
  contact    text NOT NULL,
  reason     text,
  status     text DEFAULT 'new',
  created_at timestamptz DEFAULT now()
);

-- 위젯 설정
CREATE TABLE widget_settings (
  tenant_id     uuid PRIMARY KEY,
  bot_name      text NOT NULL,
  accent_color  text NOT NULL,
  greeting      text NOT NULL,
  persona       text,
  fallback_text text,
  banned_topics text,
  position      text DEFAULT 'right',
  nudge_delay   int  DEFAULT 15,
  collect_lead  boolean DEFAULT true
);

-- 허용 도메인
CREATE TABLE allowed_domains (
  id          bigserial PRIMARY KEY,
  tenant_id   uuid NOT NULL,
  domain      text NOT NULL,
  last_seen_at timestamptz,
  UNIQUE (tenant_id, domain)
);
```

### 7.1 테넌트 격리

**모든 조회에 `tenant_id` 필터를 강제한다.** A업체 데이터가 B업체 챗봇에서 나오면 서비스는 끝난다.

```sql
SELECT content, source_id, page_no FROM chunks
WHERE tenant_id = $1                    -- 절대 빠지면 안 됨
ORDER BY embedding <=> $2
LIMIT 8;
```

애플리케이션 코드만 믿지 말고 **PostgreSQL의 Row Level Security를 함께 켠다.** 코드 실수로 필터가 빠져도 DB가 막아준다.

## 9. 예외 처리

| 상황 | 처리 |
|---|---|

## 12. 확인이 필요한 사항

1. **자동 갱신 주기** — 주 1회가 적정한지, 업체가 직접 정하게 할지
2. **대화 로그 보존 기간** — 개인정보 관점에서 90일 자동 삭제 여부
3. **파일 형식 범위** — 엑셀·PPT까지 받을지, PDF·Word로 한정할지
4. **몽골어 지원 시점** — 초기 포함인지 이후인지
5. **무료 체험 조건** — 카드 등록 요구 여부
