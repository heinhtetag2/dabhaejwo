## 1. 개요

### 1.1 시스템 내 위치

서비스는 세 개의 독립된 화면으로 구성된다.

| 구분 | 사용자 | 목적 |
|---|---|---|
| 임베드 위젯 | 업체 사이트 방문자 | 질문하고 답변받기 |
| 업체 대시보드 | 업체 담당자 | 자기 챗봇을 학습시키고 개선하기 |
| **운영 콘솔** | **자사 운영팀** | **서비스 전체를 운영하고 수익을 관리하기** |

이 문서는 세 번째를 다룬다.

### 1.2 목적

운영 콘솔은 다음 네 가지 질문에 매일 답할 수 있어야 한다.

1. 지금 손해 보고 있는 업체는 어디인가
2. 지금 고장 난 곳은 어디인가
3. 지금 응대해야 할 고객은 누구인가
4. 우리가 고객 데이터에 언제, 왜 접근했는가

### 1.3 사용자

| 역할 | 인원 | 주 사용 화면 |
|---|---|---|
| 운영 관리자 | 1~2명 | 전체 |
| CS 담당 | 1~3명 | 문의, 업체, 작업 큐 |
| 영업 담당 | 1~2명 | 업체, 요금제 |
| 개발자 | 2~3명 | 작업 큐, AI 사용량, 모델과 프롬프트 |

## 2. 설계 원칙

### 2.1 업체 대시보드와 시각적으로 구별한다

두 화면은 구조가 비슷해 혼동하기 쉽다. 운영자가 자기 콘솔인 줄 알고 고객 설정을 바꾸는 사고를 막기 위해 다음을 강제한다.

- 화면 최상단에 **내부 도구 표시 띠**를 항상 고정 노출
- 강조 색을 다르게 사용 (업체 대시보드 노랑 / 운영 콘솔 초록)
- 대리 로그인 중에는 별도 배너를 추가 노출

### 2.2 매일 볼 것은 하나만 크게 보여준다

지표 카드를 나열하면 무엇이 중요한지 사라진다. 첫 화면 최상단에는 **오늘 조치가 필요한 단 하나의 문장**만 크게 배치하고, 나머지는 그 아래로 내린다.

> 업체 42곳 중 **3곳**은 이번 달 원가가 요금을 넘겼습니다.

### 2.3 고객 데이터 접근은 기록을 남긴다

운영 콘솔은 남의 고객 데이터를 볼 수 있는 도구다. 대리 로그인과 대화 로그 열람은 사유 없이 실행되지 않으며, 기록은 삭제할 수 없다.

### 2.4 원가는 항상 보이게 한다

AI 서비스는 사용량이 곧 비용이다. 원가가 화면에서 사라지면 적자 계정을 몇 달간 방치하게 된다. 업체 목록의 기본 정렬을 원가율 내림차순으로 두는 것도 같은 이유다.

## 3. 화면 구조

```
운영 콘솔
├── 운영
│   ├── 오늘              진입 화면. 조치가 필요한 항목만
│   ├── 업체              계정 관리 · CS 대응        → 별도 문서
│   ├── 수익성            업체별 원가율과 손익
│   ├── AI 사용량         모델별 토큰 · 비용
│   └── 작업 큐           크롤링 · 임베딩 실패 복구
├── 서비스
│   ├── 요금제            플랜 정의와 한도 정책
│   ├── 모델과 프롬프트   모델 단가 · 배정 · 공통 프롬프트 · 안전장치
│   └── 기능 공개         기능 플래그
└── 지원
    ├── 문의              티켓 관리
    └── 감사 기록         고객 데이터 접근 이력
```

`작업 큐`는 운영 그룹에 함께 배치한다. 개발자만 보는 화면처럼 보이지만, 실제로는 CS 문의의 상당수가 작업 실패에서 비롯되므로 CS도 상시 확인해야 한다.

## 4. 화면별 기획

### 4.1 오늘

**목적** 로그인 직후 오늘 해야 할 일을 파악한다.

**구성**

| 영역 | 내용 |
|---|---|
| 헤드라인 | 원가 초과 업체 수를 문장으로 제시 + 수익성 화면 이동 |
| 지표 4종 | 유료 업체 수, 월 반복 매출, 오늘 총 대화, 오늘 모델 원가 |
| 조치 목록 | 유형별 배지 + 대상 + 해당 화면 이동 |
| 시스템 상태 | 응답 시간, 큐 대기, 워커 가동, 오류 건수, 최근 오류 로그 |

**조치 목록에 올라오는 항목**

| 유형 | 조건 |
|---|---|
| 원가 초과 | 이번 달 원가율 ≥ 100% |
| 작업 실패 | 재시도를 모두 소진한 작업 존재 |
| 결제 실패 | 결제 재시도 2회 이상 실패 |
| 체험 종료 | 3일 이내 무료 체험 만료 |
| 문의 | 미응답 티켓 존재 |

각 항목은 **누르면 바로 그 대상으로 이동**해야 한다. 목록에서 이름만 확인하고 다시 검색하게 만들지 않는다.

### 4.2 업체

계정 관리와 CS 대응의 중심 화면. 목록·상세·대리 로그인·쿼터 조정·내부 메모를 포함한다.

상세 기획은 **[tenant-plan.md](./tenant-plan.md)** 를 참조한다.

### 4.3 수익성

**목적** 어느 업체가 돈을 벌어주고 어느 업체가 손해인지 판단한다.

**핵심 개념**

```
원가율 = 이번 달 모델 원가 ÷ 이번 달 청구액 × 100
```

| 구간 | 판정 | 색상 |
|---|---|---|
| ~69% | 정상 | 초록 |
| 70~99% | 주의 — 인건비·서버비 제외 시 남지 않음 | 노랑 |
| 100%~ | 손실 — 쓸수록 적자 | 빨강 |

**구성**

| 영역 | 내용 |
|---|---|
| 기준 설명 | 70% 기준선의 의미를 문장으로 명시 |
| 지표 4종 | 이번 달 매출, 모델 원가, 저장 답변 비중, 원가 초과 업체 수 |
| 업체별 표 | 요금 / 모델 원가 / 원가율 막대 / 저장 답변 비율 |
| 원인 안내 | 원가 급증의 공통 패턴과 대응 액션 |

**저장 답변 비율을 함께 두는 이유**

원가율이 높은 업체는 대부분 공통 질문이 0~2개다. 자주 오는 질문까지 전부 모델로 처리하면서 비용이 쌓인다. 두 열을 나란히 두면 상관관계가 눈으로 보이고, "공통 질문을 등록하세요"라는 안내에 근거가 생긴다.

### 4.4 AI 사용량

**목적** 원가가 어디서 얼마나 발생하는지 분해해서 본다.

**구성**

| 영역 | 내용 |
|---|---|
| 지표 4종 | 오늘 처리 토큰, 오늘 원가, 대화당 평균 원가, 이번 달 누적·예상 |
| 14일 추이 | 용도별 누적 막대 (답변 생성 / 문서 학습 / 질문 벡터화) |
| 모델별 표 | 모델 × 용도별 호출 수, 입출력 토큰, 원가, 비중 |
| 상위 소비 업체 | 토큰, 원가, 대화당 원가 |
| 원가 발생 지점 | 용도별 비율 + 절감 방향 안내 |

**용도 구분**

| 용도 | 발생 시점 | 특징 |
|---|---|---|
| `answer` | 대화 한 건마다 | 원가의 대부분. 입력 토큰이 지배적 |
| `embed_doc` | 문서 업로드·재크롤링 시 | 스파이크성. 대량 업로드 시 급증 |
| `embed_query` | 대화 한 건마다 | 건당 비용은 작지만 건수가 많음 |
| `etc` | 제목 요약, 언어 감지 | 소액 |

용도를 나누지 않고 모델별로만 집계하면, 같은 모델이 답변용인지 요약용인지 구분되지 않아 절감 지점을 찾을 수 없다.

### 4.5 작업 큐

**목적** 크롤링·임베딩 작업의 실패를 발견하고 복구한다.

**구성**

| 영역 | 내용 |
|---|---|
| 지표 4종 | 대기, 진행 중, 오늘 완료·성공률, 실패 |
| 실패 목록 | 작업 종류, 대상 업체·파일, 오류 코드, 재시도 횟수, 시각 |
| 액션 | 개별 재시도, 전체 재시도, 로그 내려받기, 업체 안내 |

**주요 오류 코드와 대응**

| 코드 | 원인 | 대응 |
|---|---|---|
| `pdf_parse_timeout` | 대용량·복잡한 PDF | 타임아웃 상향 후 재시도 |
| `no_text_extracted` | 스캔 문서 또는 이미지 PDF | 업체에 안내. OCR 필요 |
| `http_404` | 삭제된 페이지 | 소스에서 자동 제외 |
| `robots_disallow` | 크롤링 차단 설정 | 업체에 robots.txt 수정 안내 |
| `rate_limited` | 모델 API 한도 | 자동 백오프 재시도 |

오류 코드는 운영자가 보는 화면인 만큼 원문 그대로 노출하되, 옆에 한글 설명을 병기한다.

### 4.6 요금제

**목적** 플랜을 정의하고 한도 초과 시 동작을 정한다.

**구성**

| 영역 | 내용 |
|---|---|
| 요금제 표 | 이름, 월 요금, 대화 한도, 문서 한도, 사용 업체 수, 판매 여부 |
| 한도 정책 | 초과 시 동작, 알림 시점 |

**설계 규칙**

- 요금제는 **삭제하지 않고 판매 중단**만 한다. 기존 계약 업체가 남아 있기 때문이다.
- 판매 중단된 구 요금제는 목록에 흐리게 유지하고 사용 업체 수를 표시한다.
- 한도 초과 시 동작은 세 가지 중 선택한다.

| 선택지 | 설명 | 권장 |
|---|---|---|
| 챗봇 중단 + 안내 표시 | 원가가 예측 가능 | 초기 권장 |
| 초과분 과금 | 매출은 늘지만 분쟁 소지 | 기업 요금제만 |
| 알림만 | 고객 경험은 좋으나 손실 위험 | 비권장 |

### 4.7 모델과 프롬프트

**목적** 원가의 기준값을 관리하고, 비용 폭주를 막는다.

**구성**

| 영역 | 내용 |
|---|---|
| 모델 단가 | 모델별 100만 토큰당 입력·출력 단가, 사용 여부 |
| 요금제별 배정 | 답변 생성 모델, 조각 수, 예상 대화당 원가 |
| 비용 안전장치 | 업체별·전체 일일 원가 상한, IP 제한, 업로드 제한 |
| 검색 설정 | 임베딩 모델, 조각 수 기본값, 답변 실패 판단 기준 |
| 공통 프롬프트 | 전 업체 공통 규칙, 답변 최대 길이 |

**단가 관리 원칙**

단가는 **코드 상수가 아니라 설정값**으로 둔다. 공급사 가격 변동과 환율에 대응해야 하기 때문이다. 다만 원가는 **호출 시점의 단가로 계산해 확정 저장**한다. 단가표 수정이 과거 데이터에 소급되면 지난달 정산이 틀어지고, 언제부터 적자였는지 추적할 수 없게 된다.

**비용 안전장치는 선택이 아니라 필수**

| 장치 | 기본값 | 없을 때 발생하는 일 |
|---|---|---|
| 업체별 일일 원가 상한 | 20,000원 | 한 업체의 버그가 하루 매출을 삼킴 |
| 전체 일일 원가 상한 | 400,000원 | 공격 시 방어선 없음 |
| IP별 분당 질문 수 | 10회 | 스크립트로 챗봇을 무제한 호출 |
| 일괄 업로드 문서 수 | 100건 | 임베딩 비용이 한꺼번에 발생 |

상한 도달 시 슬랙 알림을 즉시 발송한다.

### 4.8 기능 공개

**목적** 새 기능을 일부 업체에만 먼저 열고 반응을 본다.

**공개 대상 구분**

| 대상 | 용도 |
|---|---|
| 내부 테스트만 | 개발 중 |
| 지정 업체 | 베타 — 협조적인 업체 소수 |
| 특정 요금제 | 상위 플랜 전용 기능 |
| 전체 공개 | 정식 출시 |

기능 플래그는 코드 배포와 기능 공개를 분리해준다. 문제가 생기면 배포를 되돌리지 않고 플래그만 끄면 된다.

---

### 4.9 문의

**목적** 업체 문의를 놓치지 않고 응대한다.

**구성** 업체, 문의 내용, 경과 시간, 상태, 열기

**설계 규칙**

- 경과 시간을 기준으로 정렬한다. 오래된 것이 위로 온다.
- 티켓에서 **업체 상세로 바로 이동**할 수 있어야 한다. 문의 응대의 첫 단계는 항상 그 업체 상황 파악이다.
- 반대로 업체 상세에서도 해당 업체의 과거 문의를 볼 수 있어야 한다.

---

### 4.10 감사 기록

**목적** 운영자가 고객 데이터에 접근한 이력을 남긴다.

**기록 대상**

| 행위 | 사유 입력 |
|---|---|
| 대리 로그인 | 필수 |
| 대화 로그 열람 | 필수 |
| 요금제 변경 | 필수 |
| 쿼터 증량 | 필수 |
| 일시정지·해지 | 필수 |
| 단순 목록·상세 조회 | 불필요 |

**원칙**

- 기록은 수정·삭제할 수 없다.
- 최소 3년 보존한다.
- 업체 대시보드에서도 자기 계정에 대한 접근 이력을 확인할 수 있게 한다.

마지막 항목은 숨기는 편이 편하지만, 공개하는 쪽이 신뢰 확보에 유리하고 개인정보 처리방침 고지 의무에도 부합한다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-01 | 조치가 필요한 항목을 첫 화면에서 확인하고 해당 화면으로 이동한다 | 필수 |

## 6. 데이터 모델

업체 관리 관련 테이블은 하위 문서를 참조한다. 여기서는 운영 콘솔 전반이 의존하는 테이블만 다룬다.

> **아래 DDL 은 PostgreSQL 문법으로 쓰였고, 실제 스키마는 MariaDB 11.8 LTS 다.**
> 구현의 진실은 [`api/src/main/resources/db/migration/V1__init.sql`](../../api/src/main/resources/db/migration/V1__init.sql) 이다.
> 여기 DDL 은 어떤 데이터를 어떤 관계로 담을지에 대한 기획으로 읽고, 타입·문법은 그쪽을 따른다.
> (배열 컬럼은 조인 테이블로, `timestamptz` 는 `DATETIME(6)` + UTC 규율로 대체됐다)

```sql
-- AI 사용량 원장. 운영 콘솔의 절반이 이 테이블에 의존한다
CREATE TABLE ai_usage (
  id            bigserial PRIMARY KEY,
  tenant_id     uuid NOT NULL,
  purpose       text NOT NULL,   -- answer | embed_doc | embed_query | etc
  model         text NOT NULL,
  input_tokens  int  NOT NULL,
  output_tokens int  NOT NULL DEFAULT 0,
  cost_krw      numeric(12,4) NOT NULL,  -- 호출 시점 단가로 확정
  created_at    timestamptz DEFAULT now()
);
CREATE INDEX ON ai_usage (tenant_id, created_at);
CREATE INDEX ON ai_usage (created_at, purpose);

-- 일 단위 집계. 목록 화면은 이 테이블만 읽는다
CREATE TABLE tenant_daily_usage (
  tenant_id   uuid NOT NULL,
  day         date NOT NULL,
  conv_count  int  NOT NULL DEFAULT 0,
  saved_count int  NOT NULL DEFAULT 0,  -- 저장 답변으로 처리된 건수
  tokens_in   bigint NOT NULL DEFAULT 0,
  tokens_out  bigint NOT NULL DEFAULT 0,
  cost_krw    numeric(12,2) NOT NULL DEFAULT 0,
  PRIMARY KEY (tenant_id, day)
);

-- 모델 단가. 이력형으로 관리해 소급 변경을 막는다
CREATE TABLE model_prices (
  id             bigserial PRIMARY KEY,
  model          text NOT NULL,
  input_per_1m   numeric(12,2) NOT NULL,
  output_per_1m  numeric(12,2),
  effective_from timestamptz NOT NULL,
  created_at     timestamptz DEFAULT now()
);

-- 작업 큐
CREATE TABLE jobs (
  id          bigserial PRIMARY KEY,
  tenant_id   uuid NOT NULL,
  kind        text NOT NULL,   -- crawl | embed_doc | recrawl
  target      text NOT NULL,
  status      text NOT NULL,   -- queued | running | done | failed
  error_code  text,
  attempts    int  NOT NULL DEFAULT 0,
  max_attempts int NOT NULL DEFAULT 3,
  created_at  timestamptz DEFAULT now(),
  updated_at  timestamptz DEFAULT now()
);
CREATE INDEX ON jobs (status, updated_at DESC);

-- 기능 플래그
CREATE TABLE feature_flags (
  key         text PRIMARY KEY,
  name        text NOT NULL,
  scope       text NOT NULL,   -- internal | tenants | plan | all
  target_ids  uuid[],
  target_plan uuid,
  enabled     boolean NOT NULL DEFAULT false
);
```

### 6.1 집계 전략

`ai_usage`는 대화 한 건마다 행이 쌓이므로 빠르게 커진다. 목록과 대시보드에서 이를 직접 집계하면 업체 수와 기간에 비례해 느려진다.

| 화면 | 조회 대상 |
|---|---|
| 오늘, 업체 목록, 수익성 | `tenant_daily_usage` |
| AI 사용량 모델별 표 | `ai_usage` (월 단위, 캐시 5분) |
| 업체 상세 | `ai_usage` (실시간, 단일 테넌트) |

일 집계는 매시 정각 배치로 갱신하고, 당일분은 마지막 갱신 시각을 함께 표시한다.

## 11. 개발 단계

### 1단계 — 관측 (3주)

`ai_usage` 적재, 일 집계 배치, 오늘 화면, 업체 목록·상세, 감사 기록

원가 데이터는 **서비스 오픈과 동시에 쌓기 시작해야 한다.** 나중에 붙이면 과거 데이터가 없어 어느 업체가 언제부터 적자였는지 영영 알 수 없다.

### 2단계 — 대응 (2주)

대리 로그인, 쿼터 조정, 작업 큐, 문의

### 3단계 — 통제 (2주)

모델 단가 관리, 비용 안전장치, 요금제 정의, 수익성 화면

### 4단계 — 확장 (이후)

AI 사용량 상세, 기능 공개, 자동 알림, 이탈 예측

---

## 12. 확인이 필요한 사항

1. **원가율 경고 기준 70%** — 실제 서버비·인건비를 반영해 재산정 필요
2. **해지 업체 데이터 보존** — 벡터 데이터 즉시 삭제 여부와 유예 기간
3. **몽골 법인 대응** — 통화 표시, 결제 수단, 현지 세금계산서
4. **한도 초과 시 기본 동작** — 챗봇 중단과 초과 과금 중 어느 쪽을 표준으로 둘지
5. **운영 콘솔 접근 IP** — 재택 근무 시 VPN 구축 여부
