# 알림 기획서 — 운영 콘솔 · 업체 대시보드

> 계약은 [`docs/architecture/api-contracts.md` §11](../architecture/api-contracts.md) 이 진실 공급원이다.
> 이 문서는 **왜 이 알림들인가**를 적는다.

---

## 1. 알림이 있어야 하는 이유

두 콘솔 모두 **찾아가야만 알 수 있는** 구조였다.

- 운영자는 가입이 있었는지 알려면 업체 목록을 열어봐야 했다. 문의가 왔는지 알려면 문의 화면을 열어봐야 했다
- 업체는 학습이 끝났는지 알려면 지식 소스 화면을 새로고침해야 했다. 연락처가 왔는지 알려면 연락처 화면을 봐야 했다

둘 다 **놓치면 돈이 되는 사건**이다. 유료 전환 신청이 하루 늦게 발견되면 그만큼 매출이 늦고,
연락처는 시간이 지날수록 값이 떨어진다.

알림의 기준은 하나다 — **모르고 지나가면 손해가 나는가.** 그렇지 않은 것은 넣지 않는다.
알림이 많아지면 전부 무시하게 되고, 그때는 정작 중요한 것도 같이 묻힌다.

## 2. 원칙

| 원칙 | 이유 |
|---|---|
| **누르면 그 대상에 도달한다** | 이름만 확인하고 다시 검색하게 만들면 알림이 아니라 알림에 대한 안내다 (admin-console-plan.md §4.1 조치 목록과 같은 결) |
| **중요도와 받을 역할은 종류가 정한다** | 발행 지점이 정하면 같은 사건이 곳마다 다른 중요도로 뜬다 |
| **저장이 진실, 소켓은 편의** | 접속 중이 아닐 때 발생한 알림이 사라지면 "왔었는데 없어졌다"가 된다 |
| **중복은 키로 막는다** | 원가 상한 도달은 요청마다 발생한다. 억제가 없으면 같은 문장으로 도배된다 |
| **역할로 좁힌다** | CS 에게 원가율 알림, 개발에게 결제 알림은 소음이다 |

## 3. 운영 콘솔이 받는 것

| 알림 | 언제 | 왜 |
|---|---|---|
| **가입했다** | 가입 성공 즉시 | 영업이 가장 먼저 알아야 하는 사건. 체험 14일의 첫날이 시작됐다는 뜻이다 |
| **새 문의가 왔다** | 티켓 생성 즉시 | PG 가 붙기 전까지 **"돈 내겠다"는 신호가 이 티켓 하나뿐이다.** 놓치면 매출을 놓친다 |
| **전체 원가가 상한의 80% / 100%** | 챗봇 응답 시 검사 | 100% 면 전 업체의 챗봇이 멈춘다. 도달하고 나서 아는 것보다 낫다 |
| **한 업체가 일일 상한에 도달했다** | 챗봇 응답 시 검사 | 그 업체 챗봇이 멈췄다. CS 로 문의가 오기 **전에** 안다 |
| **원가 초과로 돌아섰다** | 매시 훑기 | 쓸수록 적자인 계정이 생겼다는 뜻. 요금제를 손볼 시점이다 |
| **체험이 3일 남았다** | 매시 훑기 | 전환 연락 시점. 하루 전은 이미 늦고 일주일 전은 잊는다 |
| **학습 실패가 5건 쌓였다** | 매시 훑기 | 한두 건은 깨진 파일이지만 다섯이면 우리 쪽 문제일 가능성이 높다 |
| ~~결제가 들어왔다~~ | — | **stub.** PG(토스페이먼츠) 미연동이라 아무도 발행하지 않는다. 자리만 미리 뒀다 |

### 넣지 않은 것

- **"토큰이 ** 이하로 떨어졌다"** — 사용자 요청에서 제외됐다. 운영자에게 의미 있는 축은 토큰 잔량이 아니라 원가율이고, 그건 위의 원가 알림 셋이 이미 덮는다

## 4. 업체 대시보드가 받는 것

| 알림 | 언제 | 왜 |
|---|---|---|
| **운영팀이 접속했습니다** | 대리 접속 시작 즉시 | **사후 이력보다 실시간 알림이 훨씬 강한 신뢰 장치다** (tenant-plan.md §6.3). 사유를 그대로 보여준다 — 업체에게 공개된다는 전제로 받은 값이다 |
| **이번 달 대화의 80% 를 썼다** | 매시 훑기 | 미리 알아야 요금제를 올리든 아끼든 한다 |
| **한도를 다 썼다** | 매시 훑기 | 챗봇이 멈춘다. **갑자기 멈추는 경험은 해지로 직결된다** |
| **무료 체험이 3일 남았다** | 매시 훑기 | 학습해 둔 것을 잃지 않으려면 미리 정해야 한다 |
| **문서 학습이 끝났다 / 실패했다** | 인덱싱 종료 즉시 | 업로드하고 나면 언제 끝나는지 알 수 없었다. 실패는 특히 — 조용히 두면 학습된 줄 알고 기다린다 |
| **새 연락처가 도착했다** | 리드 등록 즉시 | 업체 입장에서 이게 곧 매출이다. 시간이 지나면 값이 떨어진다 |
| **답 못한 질문이 10건 쌓였다** | 매시 훑기 | 공통 질문으로 올리면 다음부터 바로 답한다. 매번 알리면 알림이 무의미해지므로 문턱을 둔다 |

> **"누가 로그인했다"의 정체** — 처음 요청은 로그인 알림이었으나, 실제로 알아야 하는 것은
> 팀원의 평범한 로그인이 아니라 **운영팀의 대리 접속**이다(사용자 확인). 팀원 로그인까지
> 알리면 매일 아침 알림이 쌓이고, 그 소음에 대리 접속 알림이 묻힌다.

> **"토큰"의 뜻** — 업체 화면에서 토큰은 **대화 수**를 가리킨다 (tenant-plan.md §1.3 용어표).
> 그래서 한도 알림의 단위는 건수다. 모델 토큰은 업체에게 보여주지 않는다.

## 5. 발행 시점 — 즉시 vs 훑기

| | 즉시 | 매시 훑기 (`NotificationSweeper`, 매시 20분) |
|---|---|---|
| 성격 | **순간**이 있다 | 시간이 지나며 **사실이 되어 있을 뿐**이다 |
| 예 | 가입·문의·대리 접속·리드·학습 종료 | 한도 80%·체험 3일 전·원가 초과·답변 공백 누적 |
| 중복 억제 | 대개 불필요 (매번 새 사건) | 필수 — 매시 돌아도 같은 알림은 한 번만 |

훑기가 **정각이 아니라 20분**인 이유: 일 집계(`DailyUsageAggregator`)가 정각에 돈다.
같은 시각에 돌면 방금 지난 한 시간의 사용량이 빠진 채로 판단하게 된다.

원가 상한 알림만 `publishDetached`(별도 트랜잭션)다. 상한에 걸린 요청은 거절되며 롤백되는데,
같은 트랜잭션에 있으면 **"상한에 도달했다"는 사실까지 되감겨** 아무도 모르게 된다.

## 6. 화면

두 콘솔 모두 상단 우측 **벨 + 드롭다운**. 별도 전체 목록 화면은 두지 않았다 —
알림은 최근 것이 전부이고, 지난 알림을 뒤지는 일은 감사 기록·문의 화면이 담당한다.

- 배지는 안 읽음 수. 소켓이 갱신하고 60초 폴링이 보험이다
- 목록은 **벨을 열었을 때만** 읽는다. 배지만 보려고 매번 30건을 끌어올 이유가 없다
- 안 읽음은 배경색으로 구분하되 중요도는 색만으로 구분하지 않는다 — 스크린리더용 라벨을 함께 낸다 (WCAG 2.1 AA)
- 누르면 읽음 처리 + `targetPath` 로 이동

## 7. 한계 (알고 두는 것)

- **소켓 세션이 인스턴스 메모리에만 있다.** 서버가 여러 대가 되면 A 에 붙은 사용자는 B 에서 발생한 알림을 실시간으로 못 받는다. 다만 **알림 자체는 DB 에 남아 목록에는 보인다** — 레이트 리밋·스케줄러와 같은 종류의 한계다 (`docs/IMPROVEMENTS.md`)
- 훑기도 인스턴스마다 돈다. 결과는 같다 — 유니크 인덱스가 두 번째를 떨어뜨린다
- **알림은 화면에만 뜬다.** 메일(`Mailer`)은 로그인 코드·초대에만 쓰고 알림에는 붙이지 않았다. 슬랙(`#ops-alert`)은 아직 없다 — 콘솔을 안 보고 있으면 못 본다. 원가 상한 같은 HIGH 는 결국 밖으로 나가야 한다 (`docs/IMPROVEMENTS.md`)
