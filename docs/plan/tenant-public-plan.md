## 1. 개요

### 1.1 무엇을 만드는가

지금 `tenant/` 는 **로그인한 업체 담당자**만을 위한 화면이다. 계약을 어떻게 시작하는지가 없다.
이 문서는 그 앞단 — 서비스를 알리고, 요금을 보여주고, 가입시키는 영역을 다룬다.

```
방문 → 서비스 안내 → 요금제 확인 → 가입 → (챗봇 설치) → 유료 전환
                                    ↓
                              업체 대시보드
```

### 1.2 사용자

[tenant-plan.md](./tenant-plan.md) §1.2 의 그 사람들이 **아직 고객이 아닌 상태**다.

| 유형 | 여기서 알고 싶은 것 |
|---|---|
| 쇼핑몰 운영자 | 우리 사이트에 붙일 수 있나? 얼마인가? 얼마나 걸리나? |
| CS 담당 | 문의가 실제로 줄어드나? |
| 대표·결정권자 | 월 얼마고 해지가 되는가? |
| 외주 개발자 | 설치가 스크립트 한 줄이 맞나? |

### 1.3 설계상 가장 중요한 전제

**이 페이지의 목적은 설명이 아니라 가입이다.** 기능을 나열하면 읽다가 닫는다.
[tenant-plan.md](./tenant-plan.md) §1.4 가 정의한 성공 조건이 여기서도 그대로 적용된다 —
"가입 후 30분 안에 챗봇이 자기 사이트에 떠 있어야 한다."

그러므로 **가입 앞을 막는 것을 최대한 치운다.** 특히 카드 등록(§5.2 참조).

## 2. 설계 원칙

### 2.1 용어를 하나로 쓴다

"패키지"·"플랜"·"상품"을 섞어 쓰지 않는다. **요금제**로 통일한다.
운영 콘솔(`plans` 테이블, 요금제 화면)과 업체 대시보드(요금제 화면)가 이미 그 말을 쓰고 있다.
공개 페이지만 다른 말을 쓰면 가입한 사람이 같은 것을 두 이름으로 만나게 된다.

### 2.2 요금은 DB 에서 읽는다

가격을 페이지에 적어두지 않는다. `plans` 테이블이 진실이며 공개 페이지는 그것을 읽는다.
운영자가 요금제를 바꿨는데 소개 페이지가 옛 가격을 보여주면, 그 차이가 그대로 분쟁이 된다.

`sellable = false` 인 요금제는 공개 페이지에 나오지 않는다 — 판매 중단된 구 요금제다.

### 2.3 없는 기능을 있는 것처럼 적지 않는다

지금 없는 것: 실 결제(PG 미연동), 답변 파이프라인, 크롤러.
"AI가 자동으로 학습합니다"처럼 적어두면 가입한 사람이 곧바로 배신감을 느낀다.
**할 수 있는 것만 적고, 준비 중인 것은 준비 중이라고 적는다.**

### 2.4 공개 페이지는 서버에서 그린다

검색으로 들어오는 것이 유일한 유입 경로다. 대시보드처럼 클라이언트에서 데이터를 불러
그리면 검색 엔진이 빈 페이지를 본다. 공개 영역은 Server Component 로, 대시보드는
지금처럼 클라이언트로 둔다. 번들도 자연히 갈린다.

## 3. 화면 구조와 라우팅

### 3.1 지금 문제

현재 `/` 가 대시보드 홈이다. 공개 랜딩을 `/` 에 두려면 대시보드가 비켜야 한다.

### 3.2 제안 — 대시보드를 `/app` 아래로

```
tenant/
├── /                     서비스 안내 (랜딩)        ← 공개
├── /pricing              요금제                    ← 공개
├── /signup               가입                      ← 공개
├── /login                로그인                    ← 공개
├── /terms · /privacy     이용약관 · 개인정보처리방침 ← 공개
└── /app/…                업체 대시보드 10화면       ← 로그인 필요
    ├── /app              홈
    ├── /app/improve      답변 개선
    ├── /app/conversations · /app/leads
    ├── /app/sources · /app/faq · /app/appearance · /app/install
    └── /app/plan · /app/team
```

`/dashboard` 가 아니라 `/app` 인 이유는 API prefix(`/api/app/**`)와 같은 말을 쓰기 위해서다.
같은 영역을 두 이름으로 부르면 코드에서 계속 번역하게 된다.

**이 이동의 비용**: 페이지 파일 11개 위치 변경, `shared/config/routes.ts` 상수, 화면 안의 링크.
지금이 가장 싸다 — 외부에 공개된 URL 이 아직 없다.

### 3.3 로그인 후 이동

로그인 성공 → `/app`. 이미 로그인된 상태로 `/login`·`/signup` 에 오면 `/app` 으로 보낸다.

## 4. 화면별 상세

### 4.1 서비스 안내 (`/`)

**목적** 3초 안에 "이게 뭔지"를 이해시키고 가입으로 보낸다.

| 영역 | 내용 |
|---|---|
| 히어로 | 한 문장 정의 + 가입 버튼 + 설치 코드 한 줄 미리보기 |
| 어떻게 동작하나 | 3단계 — 주소 등록 → 학습 → 스크립트 붙이기 |
| 무엇이 좋아지나 | 문의 감소, 야간 응대, 놓친 질문을 답으로 채우는 루프 |
| 실제 화면 | 대시보드·위젯 스크린샷 |
| 요금 요약 | 무료 체험 강조 + 요금제 페이지로 |
| 자주 묻는 질문 | 설치 난이도, 해지, 데이터 보관, 지원 언어 |

**히어로 문장**은 기능이 아니라 결과를 말한다.

> 홈페이지에 한 줄만 붙이면, 우리 사이트를 학습한 챗봇이 방문자 질문에 답합니다.

**설치 코드를 히어로에 보여준다.** 이 제품의 가장 큰 강점이 "붙이기 쉽다"이고,
그건 설명보다 코드 세 줄을 보여주는 편이 빠르다.

### 4.2 요금제 (`/pricing`)

**목적** 얼마인지, 무엇이 다른지, 어떻게 시작하는지.

| 영역 | 내용 |
|---|---|
| 요금제 카드 | `plans` 에서 `sellable = true` 인 것만, `sort_order` 순 |
| 비교표 | 대화 한도, 문서 한도, 월 요금 |
| 한도 안내 | 한도를 넘으면 어떻게 되는지 |
| 자주 묻는 질문 | 결제 주기, 변경, 해지, 세금계산서 |

**한도 초과 동작을 반드시 적는다.** [admin-console-plan.md](./admin-console-plan.md) §4.6 이
"챗봇 중단 + 안내 표시"를 초기 권장으로 정했다. 이건 고객이 가입 전에 알아야 하는 사실이다 —
모르고 계약했다가 어느 날 챗봇이 멈추면 그대로 해지 사유다.

> 한도에 닿으면 챗봇이 답변을 멈추고 안내 문구만 표시합니다. 초과 요금은 청구되지 않습니다.

**"저장 답변은 한도를 쓰지 않는다"를 여기서도 알린다.** 공통 질문을 등록할수록 한도가 덜
소모되며, 이건 우리 원가에도 좋다 ([tenant-plan.md](./tenant-plan.md) §4.9).

**기업 요금제**(`negotiable = true`)는 금액 대신 "문의"를 보여준다.

### 4.3 가입 (`/signup`)

**목적** 최소 입력으로 계정과 업체를 만들고 대시보드로 보낸다.

**입력 항목**

| 항목 | 필수 | 비고 |
|---|:--:|---|
| 이메일 | ● | 로그인 아이디이자 담당자 |
| 비밀번호 | ● | 8자 이상 |
| 업체명 | ● | 대시보드·챗봇 이름의 기본값이 된다 |
| 홈페이지 주소 | ● | 학습 대상이자 위젯 허용 도메인 |
| 약관 동의 | ● | 이용약관 + 개인정보처리방침 |

**한 화면에 끝낸다.** 단계를 나누면 이탈한다. 다섯 줄이면 한 화면에 들어간다.

**가입이 만드는 것** — 하나라도 실패하면 전부 되돌린다.

| 대상 | 값 |
|---|---|
| `tenants` | `status = TRIAL`, `trial_ends_at = 오늘 + 14일`, `publishable_key` 발급 |
| `tenant_members` | 입력한 이메일, `role = OWNER`, `invite_state = ACCEPTED` |
| `bot_settings` | 업체명 기반 기본값 |
| `allowed_origins` | 입력한 홈페이지 주소(호스트만) |

가입 직후 **로그인 상태로 `/app` 에 도착**한다. 다시 로그인하게 만들지 않는다.

**체험 기간 14일**은 이 문서에서 처음 정하는 값이다. 근거는 §5.1.

### 4.4 이용약관 · 개인정보처리방침 (`/terms`, `/privacy`)

**목적** 가입 화면의 동의 체크가 가리키는 실체.

지금 단계에서는 **초안 자리만 만든다.** 법무 검토 없이 쓴 약관을 게시하면 없느니만
못하다. 페이지와 라우트는 만들되 본문은 "준비 중이며 정식 공개 전 게시합니다"로 두고,
`docs/IMPROVEMENTS.md` 에 P0 으로 등록한다.

개인정보처리방침에는 **운영팀 대리 접속**을 반드시 명시해야 한다
([tenant-plan.md](./tenant-plan.md) §6.3 이 그 고지 의무를 근거로 이력 공개를 정했다).

### 4.5 로그인 (`/login`)

이미 있다. 공개 셸(헤더·푸터)에 맞추고, 가입 링크를 추가한다.

## 5. 정책 결정

### 5.1 무료 체험 — 카드 없이 14일

[tenant-plan.md](./tenant-plan.md) §12-5 의 미결 항목("무료 체험 조건 — 카드 등록 요구 여부")을
여기서 정한다.

**카드를 받지 않는다.** 근거:

1. 이 제품의 승부처는 가입 후 30분이다(§6). 카드 입력은 그 앞을 막는다.
2. 애초에 **PG 가 연동되어 있지 않다.** 받을 방법이 없다.
3. 남용 비용은 체험 한도로 이미 제한된다 — `TRIAL` 은 대화 100건 / 문서 30건이다.
   [admin-console-plan.md](./admin-console-plan.md) §4.7 의 일일 원가 상한도 별도로 걸린다.

**14일**로 정한 이유는, 사이트를 학습시키고 답변을 몇 번 다듬어 효과를 확인하려면
주말이 두 번 필요하기 때문이다. 7일이면 설치만 하다 끝난다.

체험 종료 3일 전 알림은 [admin-console-plan.md](./admin-console-plan.md) §114 의
"체험 종료" 작업 큐 항목과 이어진다.

### 5.2 결제 — 지금은 신청, 나중에 자동

**PG 가 연동되어 있지 않다.** 결제 화면을 만들어 카드번호를 받는 시늉을 하는 것은
[workflow-rules](../../.claude/rules/workflow-rules.md) 의 "조용한 성공 처리 금지"를 정면으로 어긴다.

두 단계로 나눈다.

| 단계 | 유료 전환 방식 | 상태 |
|---|---|---|
| **1단계 (지금)** | 요금제 선택 → 신청 → `tickets` 에 문의로 적재 → 운영팀이 계약·수납을 수동 처리 | 만들 수 있음 |
| 2단계 (PG 연동 후) | 카드 등록 → 정기 결제 → 영수증·세금계산서 | `PaymentGateway` stub 교체 |

1단계에서 화면은 **정직하게 적는다.**

> 지금은 담당자가 직접 안내해 드립니다. 신청하시면 1영업일 안에 연락드립니다.

`billing_records` 는 운영팀이 수납을 확인한 뒤 기록한다. 자동 생성하지 않는다 —
받지 않은 돈을 받은 것으로 적으면 정산이 틀어진다.

### 5.3 도메인 중복 등록

서로 다른 업체가 같은 도메인을 등록할 수 있다. 위젯 키가 다르므로 동작 충돌은 없고,
남의 사이트에 스크립트를 넣을 수 있는 사람은 그 사이트 주인뿐이라 실질 위험은 낮다.

**지금은 막지 않는다.** 도메인 소유 확인(DNS TXT·파일 업로드)은 가입 마찰을 크게 키운다.
경쟁사 도메인 선점 같은 문제가 실제로 생기면 그때 넣는다 — Open Question 으로 남긴다.

### 5.4 가입 남용

이메일 확인 절차가 없으므로 가짜 이메일로 체험 계정을 반복 생성할 수 있다.

| 방어 | 지금 |
|---|---|
| 체험 한도 | ● 대화 100 / 문서 30 |
| 일일 원가 상한 | ● `cost_guards` |
| 가입 IP 레이트 리밋 | ○ 필요 |
| 이메일 인증 | ○ Mailer 미연동 |

**가입 IP 레이트 리밋은 이번에 넣는다.** 나머지는 메일 발송이 붙을 때 함께 한다.

## 7. API

공개 페이지는 **인증 없이** 요금제를 읽어야 한다. 지금 `SecurityConfig` 는
`/api/auth/**` 와 `/actuator/health` 만 열려 있고 나머지는 거부한다.

### 7.1 인증 경계가 4종이 된다

[CLAUDE.md](../../CLAUDE.md) 의 "인증 3종 분리" 결정에 **공개 영역을 명시적으로 추가**한다.
주체가 없는 요청이라 기존 셋 중 어디에도 속하지 않는다.

| Prefix | 주체 |
|---|---|
| `/api/ops/**` | 운영자 |
| `/api/app/**` | 업체 담당자 · 대리 접속 |
| `/api/widget/**` | 방문자 (공개 키 + Origin) |
| **`/api/public/**`** | **없음 — 누구나 읽는 정보만** |

`/api/public/**` 에는 **쓰기 엔드포인트를 두지 않는다.** 가입은 `/api/auth/app/signup` 이다
— 인증을 만들어내는 행위이므로 auth 쪽이 맞고, 레이트 리밋도 거기 붙는다.

### 7.2 엔드포인트

| Method | Path | 설명 |
|---|---|---|
| GET | `/api/public/plans` | 판매 중인 요금제. `sellable = true` 만 |
| POST | `/api/auth/app/signup` | 가입 → 로그인 토큰까지 반환 |
| POST | `/api/app/plan/upgrade-request` | 유료 전환 신청 → `tickets` 적재 |

```json
{ "id": "p2...", "code": "BUSINESS", "name": "비즈니스",
  "monthlyFee": 89000, "negotiable": false,
  "convLimit": 3000, "docLimit": 500 }
```

`tenantCount` 는 내보내지 않는다 — 운영 콘솔의 §7 요금제 응답에는 있지만,
"이 요금제를 몇 곳이 쓰는지"는 대외 공개 정보가 아니다.
**같은 리소스에서 필드를 빼는 것만 허용된다**([api-contract-rules](../../.claude/rules/api-contract-rules.md)).

```json
{ "email": "...", "password": "...", "tenantName": "노르드하임 가구",
  "primaryDomain": "nordheim.co.kr", "termsAgreed": true }
  → { "accessToken", "refreshToken", "member" }
```

응답 형태는 `POST /api/auth/app/login` 과 같다. 가입 직후 로그인 상태가 되어야 하고,
클라이언트가 두 응답을 다르게 다룰 이유가 없다.

## 8. 예외 처리

| 상황 | 처리 |
|---|---|
| 이미 가입된 이메일 | "이미 가입된 이메일입니다. 로그인해 주세요" + 로그인 링크 |
| 홈페이지 주소 형식 오류 | 예시와 함께 즉시 안내 (`shop.example.com`) |
| 약관 미동의 | 가입 버튼 비활성 |
| 가입 시도 과다 | `RATE_LIMITED`. "잠시 후 다시 시도해 주세요" |
| 요금제 목록 조회 실패 | 가격을 숨기고 "문의" 안내. **옛 가격을 캐시로 보여주지 않는다** |
| 로그인 상태로 `/signup` 접근 | `/app` 으로 이동 |
| 체험 만료 후 로그인 | 로그인은 허용하고 대시보드에 전환 안내 배너. 잠그지 않는다 |

**체험 만료를 잠그지 않는 이유**: 잠그면 유료 전환을 하고 싶어도 못 한다.
챗봇 응답만 멈추고 대시보드는 열어둔다.

## 10. 개발 단계

### 1단계 — 뼈대 (필수)
라우팅 재배치(`/app`), 공개 셸(헤더·푸터), 로그인 연결, 가입 화면과 `signup` API

### 2단계 — 내용
서비스 안내 본문, 요금제 페이지와 `/api/public/plans`, 자주 묻는 질문

### 3단계 — 전환
유료 전환 신청 → 문의 적재, 체험 만료 배너, 약관·개인정보처리방침 초안

### 4단계 — 이후
이메일 인증, PG 연동과 카드 결제, 다국어, 블로그·고객 사례

## 11. 확인이 필요한 사항

1. **체험 14일 · 카드 없음** — §5.1 에서 정했다. 다르게 갈지

6. **랜딩에 쓸 실제 스크린샷** — 데모 업체(노르드하임)로 찍을지, 실제 고객 사례를 기다릴지
