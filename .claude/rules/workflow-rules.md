# Workflow Rules — 작업 절차와 품질 게이트 (스택 무관)

## 설계 먼저
- 새 기능은 데이터/인터페이스 정의가 첫 단계다. API가 있는 프로젝트는 `docs/architecture/api-contracts.md` 수정이 항상 코드보다 먼저 (api-contract-rules.md).
- 기획서/계약에 없는 필드·기능을 "있으면 좋을 것 같아서" 추가 금지 — `docs/intake.md`의 Open Question으로 기록 후 확인.

## Stub 정책 (외부 의존성)
파일 저장소, 결제, 푸시/알림, 이메일, 외부 API 연동 같은 외부 의존성은 **임의로 구현하지 않는다.**
- 인터페이스를 정의하고 로컬/더미 구현을 stub으로 둔다.
- 코드에 `// TODO(stub): <무엇이 미구현인지>` 주석 필수.
- `CLAUDE.md > 미완료/Stub 목록`에 항목과 필요 시점을 기록.
- stub이 "동작하는 척"(상태만 바꾸고 실제 동작 없음) 할 때는 로그로 stub임을 명시. 조용히 성공 처리 금지.

## 상태 전이 검증
- 상태(enum)를 가진 도메인은 **허용 전이를 코드로 먼저 정의**한다.
- 모든 상태 변경은 전이 정의를 통과시킨다. 무효 전이는 명시적 에러. "일단 값만 바꾸기" 금지.

## 미루기 관리 (IMPROVEMENTS.md)
- 지금 안 고치기로 한 문제는 `docs/IMPROVEMENTS.md`에 등록:
  - **P0**: 런칭/배포 차단 — 다음 마일스톤보다 먼저
  - **P1**: 기능 결함이지만 우회 가능
  - **P2**: 개선/리팩토링
- 하드코딩 임시값(계산식, 더미 금액 등)은 만드는 순간 즉시 등록. 나중에 발견되길 기대하지 않는다.
- rules 자체가 이 프로젝트와 안 맞으면 `[harness]` 태그로 등록 → 팩토리(E:\_agent)로 환류 (HARNESS.md 진화 루프).

## 테스트
- 핵심 비즈니스 로직, 상태 전이, 권한 체크는 테스트 필수 (성공 + 거부 케이스 모두).
- 테스트 환경은 운영과 같은 종류의 의존성 사용 (DB가 MySQL이면 테스트도 MySQL — 대체 DB로 거짓 통과 만들지 않기). 구체 도구는 스택 모듈이 정의.

## 금지
- 같은 데이터를 표현하는 타입/모델을 용도별로 복제 금지 — 단일 표현 + 부분집합.
- 검증(빌드/테스트)이 깨진 상태로 마일스톤 완료 기록 금지.
